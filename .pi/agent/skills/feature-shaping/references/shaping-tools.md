# Small tools for shaping

Read this when a framed feature remains fuzzy or an unknown blocks a pitch.
Pick the smallest tool that answers **that** question. There is no fixed
sequence. Return to the pitch's rough level after a concrete mock or spike.

- **TRACE** when “make this better” lacks a specific failure: follow a real
  person's job from start to finish, including work outside the product.
  Flag detours and compensating behavior; retain the problem spots and
  evidence.
- **DUMP** when ideas arrive faster than they can be evaluated: record them
  unstructured. Do not assume each is a requirement; retain relevant
  candidates.
- **AFFINITIZE** when a pile obscures the main pieces: group into a small
  number of initially **unnamed** clusters. Name them only after seeing what
  belongs together; revise them as you learn.
- **CONTRAST** when one approach seems inevitable but feels wrong: put
  meaningfully different approaches side by side. An imperfect option can
  expose a trade-off. Choose against the frame and appetite.
- **BREADBOARD** when interaction is uncertain: list places, affordances
  (including informative copy), and connections. Play through the core job,
  intermediate states, and outcome without committing to layout.
- **FAT MARKER SKETCH** when two-dimensional arrangement is itself uncertain:
  draw essential placement and hierarchy in broad strokes, not a finished UI.
- **INTERRELATE** when you cannot tell which questions unlock others: draw
  `A → B` when resolving A helps resolve B. Examine upstream elements and
  tightly linked groups. This is a reasoning aid, not the final task graph
  or a declaration of concept boundaries.
- **MOCK** when wording or interaction states cannot be judged abstractly:
  make only the screen states needed to test that doubt, not a high-fidelity
  handoff.
- **SPIKE** when a technical assumption may hide unbounded change: do a
  short, throwaway check of the critical integration, data, or migration path.
  Seek evidence of a stopping point and record what remains unknown. A spike
  does not become production code without a separate decision.

During **kickoff**, builders may DUMP provisional work, AFFINITIZE it into
initially unnamed groups, then name tentative integrated scopes and identify
which are still uphill. Actual scopes and tasks emerge while building. Prefer
slices demonstrable end to end; do not convert a diagram into preassigned
work.
